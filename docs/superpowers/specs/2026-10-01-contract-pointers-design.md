# 契约只放判法与出处：工作规矩进记忆，字数线 5000

日期：2026-10-01。只动本仓 `SKILL.md`。spec 与计划在收尾时删除。审查：`external:/home/xy/.claude-subagent/reports/xy-goal-pointers/spec-review-detail.md`。

## 问题

用户原话（2026-10-01）：「我感觉 1 万多字其实已经能表达非常多的信息了，这个信息量我觉得非常过载」；看到 21 段通用原话永远退不了场后：「这说明我们的规矩有问题……你要根据铁律来优化它」。决定权交给 main，要有依据。

在用的那份契约当时的构成（全文约 2.6 万字）：

| 部分 | 字数 | 病因 |
|---|---|---|
| 我写的部分 | 约 12,300 | 见下三行 |
| 　未完成条目的判据 | 约 5,300 | 抄了设计内容：一条 1,300 字，把整套设计复述一遍，而 spec、代码、原话里各有一份；用户改口后旧说法还留着，只能再追加一句打补丁 |
| 　未完成条目的产物 | 约 2,500～2,800 | 夹着过程记录 |
| 　已取消条目 | 约 2,000 | 每条带长引文 |
| 用户原话 | 约 13,800 | 其中 21 段（2,669 字）挂在「全部未完成条目」上，退场条件「指到的条目都已验收」永远不成立 |

两条根因：

1. **拷贝代替指针，且旧字退不了场**。判据被写成设计内容的副本，副本会过期、和正本矛盾；「判据只能往后加」让过期的字删不掉；已取消条目的长引文同理。
2. **边界没划清**：契约里混进了不属于它的东西——工作方式（「用 codex 别用 deepseek」「自查时附搜索结果」是怎么干活的规矩，不是这个目标的交付物）与过程记录。

外部做法（联网查过）：Anthropic 长任务 harness 的任务清单每条只有一句描述、几步验证和「是否通过」，agent 只许改「是否通过」（[effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）；上下文工程讲「找能最大化目标达成概率的最小高信号 token 集」（[context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）；Claude Code 官方最佳实践：每一行都问删掉它会不会让 Claude 犯错，不会就删（[best practices](https://code.claude.com/docs/en/best-practices)）；HumanLayer 建议引用而不是拷贝（[writing a good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md)）。

## 决定

| # | 决定 |
|---|---|
| D1 | **一条未完成条目 = 标题一句 + 判据 + 出处 + 产物**，以 300 字为度。判据只写怎么判完成（可核实）；出处写原话编号与 spec／文档路径，没有原话指到的条目也写在这里（「来源：…」，原来的行末「来源」并进出处）；产物写现状指针与还差什么。**设计内容不进契约**，契约只指过去。**出处必须指向能活到该条目验收的东西**：指向的 spec、文档、工作树要被删或合入时，先把出处改指到新家（合入的提交、仓库文档），再删它。 |
| D2 | **判据的改动**：新原话带来新要求，出处加编号、必要时判法加一句；用户改口，**当场**把判法改成最新口径、出处加编号，不让旧口径与新原话并存。凡是删字或改写，改之前存一份原文（自上次核对以来已存过就不再存），在下一次送验时由子代理按「清理」第 4 步核对没丢要求、没放宽（放宽必须有原话撑着）。「判据只能往后加」这句删掉。 |
| D3 | **原话标注**：① 带目标要求的 → 落到条目；② 工作方式类的通用指示（怎么干活、用什么工具、汇报什么格式）→ 当场写进持久的工作规矩（记忆、CLAUDE.md 或对应 skill），标「（原话 N → 规矩：<写在哪>）」；③ 只是提问、确认，没提出也没改动任何事的，以及不带可跟踪要求的催促、状态查询、命令展开（某个 skill 的固定文字）→ 标「→ 无：<为什么>」，命令展开只记一行、不抄展开文字。一段两类都有就并写「（原话 N → T3；规矩：…）」。去掉「全部未完成条目」这一类。删除条件：落点全进「已验收」或已成 `[~]`；「规矩」由送验子代理核对写进去的意思与原话一致（规矩后来又被新原话改了，就按新段重写同一处、新段标「规矩：同处」，旧段只核当时确实按它处置了）；「无」由子代理确认不带要求。并写的段，各部分的条件都满足才删。 |
| D4 | **已取消条目只留一行**：「- [~] ID 一句话（原话 N：「不超过 30 字的摘句」）」。摘句由下一次送验的子代理对照原话核对——「取消」与「暂缓」的性质、限定条件不许丢——核过才删那段原话。 |
| D5 | **字数线 5000**：我写的部分（「## 用户原话」之前）达到 5000 字就在那次自查里做完整清理（原来 12000）。依据：9～10 条在办的事 × 300 字 + 头部、已验收、已取消约 1000 字 ≈ 4000，线定 5000（留约四分之一）。用户原话不计入、不压缩；有了 D3，原话只剩指向未完成条目的那些。 |
| D6 | **自查 prompt 同步**：12000 改 5000；两头核对认 D3 的标注，并查条目出处里的原话编号都还在、标注也指回这一条；读条目时「先按出处把要求找齐」。SKILL.md 写一句与版本无关的话：定时器文案在建时冻结，skill 改版后把在跑的定时器删掉、按新文案重建。 |
| D7 | **验收按出处还原要求**：验收子代理的要求加一条——按每条的出处把完整要求找齐再核（原话读契约里那几段，spec／文档按路径去读；出处指向的东西不在了先报，不许跳过）。 |
| D8 | **skill 自身按铁律压**：长句拆短、删重复说法，规则只说一遍——自查 prompt 例外（压缩后只有它还在，重复是功能）。 |

不做：不加脚本或工具；关闭流程不动。目录里 14 份旧契约的核实与归档另行处理，不在本 spec。
